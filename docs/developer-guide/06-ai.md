# 6. AI features

AI is an *optional layer*. The product works fully with it off, and it is **off by default** on the server. The design
record and the reasons behind each decision are in [`docs/AI_CFO_DESIGN.md`](../AI_CFO_DESIGN.md); this page is the map of
how it is built.

## What uses a model

| Feature | Where it appears | Route / code | Model's job |
|---|---|---|---|
| **Daily briefing** | Dashboard card | `POST /api/ai/briefing`, `lib/briefingRoutes.ts` | Write one or two sentences on why true profit moved, and up to four "attention" items |
| **Ask your business** | Floating button on every tab | `POST /api/ai/chat`, `lib/chatRoutes.ts` | Answer a question about the business in words; for "what if I change prices" it asks the app to run a calculation |
| **Order reading (web)** | Paste box in Add Order | `POST /api/ai/parse-order`, `lib/orderParseRoutes.ts` | Read a pasted WhatsApp-style order into form fields |
| **Production reading (web)** | Note box in Log Production Run | `POST /api/ai/parse-production-run`, `lib/productionParseRoutes.ts` | Read "made 40 croissants, 3 burnt" into form fields |
| **Phone readings** | Stockpot Quick | `POST /api/mobile/parse`, `lib/quickParseRoutes.ts` | The same, for four kinds: order, stock bought, something made, a payment |

The model is `claude-haiku-4-5` (`AI_MODEL` in `lib/aiConfig.ts`), called through the Anthropic SDK with structured
(JSON-schema) outputs. One shared client is created lazily in `lib/anthropic.ts` (30 s timeout, 2 retries); the server
boots without a key and only an AI request fails. Provider errors are mapped to friendly messages by `aiErrorResponse`
and are never forwarded.

## The two rules that shape everything

### Rule 1: the model writes words, never numbers (briefing and chat)

This is enforced by code, not by asking nicely.

- The business is described to the model by a **snapshot** (`src/utils/aiSnapshot.ts`) built **in the browser** from the same
  functions the screens use (`profit.ts`, `customers.ts`, `pricing.ts`, `reorder.ts`). The server never recomputes anything,
  so a number in an answer is a number the screens already show.
- Every number is a **figure** in a registry with an id (`{kind, value, label}`; kinds: money, percent, count, days, date,
  quantity). Changes, percentages and the ordering of "drivers" are all computed in code before the model sees them.
- The model's text may contain only words and **tokens**: `{{fig:ID}}`, `{{name:ID}}`, `{{cust:LABEL}}`. It must not write
  a digit, a spelled-out number ("twelve", "percent", "dozen"), a currency symbol or a percent sign.
- `validateAiText` (`src/utils/aiFigures.ts`) rejects text with any digit or number-word outside a token, a token whose id is
  not in the registry, malformed output, or text over the length limit. The check runs **on the server** before anything is
  stored or returned; the browser then renders tokens from its own registry (`renderAiText`) and shows a dash for an unknown one.
- On rejection the request is retried **once**, with the rejection reasons fed back to the model. If it fails again, the screen
  uses a **deterministic** explanation built by code from the same snapshot (the briefing) or says the explanation is
  unavailable (chat). A rejected answer is never shown.
- Headlines, tiles, tables and charts are never model output. The browser renders tokens into formatted text
  (`formatFigure`: `₹`, Indian digit grouping, signs) from the registry.

What the guard cannot do: tell whether a sentence is *wrong* (blaming the wrong driver). Only that it carries no invented
number. Drivers are computed and ordered by code, and the prompt tells the model to explain only what the snapshot lists.

### Rule 2: the model reads; code decides (order, production, restock, payment readings)

For turning free text into data (the web paste boxes and the phone), the model's answer is a **claim to be checked**:

- Every quantity, price and discount the model returns must appear in the message (`numberWritten`).
- Every name, phrase and address must be text that is in the message.
- An item is only matched to a menu item that exists (ids must be among those sent); when several menu items could match
  ("Pumpkin Seed Bread 350g" and "500g"), **the words decide in code** (`src/utils/menuVariants.ts`), not the model.
- Dates are never worked out by the model: it returns the phrase as written ("tomorrow", "Saturday", "12 Oct") and
  `resolveWhen` works it out from the business's date.
- Anything left open becomes a **question** for the owner, never a guess.
- **Nothing is saved from a reading.** The web pre-fills a form; the phone shows a confirm screen. The owner confirms.

The check functions live next to the schema in `src/utils/orderParse.ts`, `productionParse.ts`, `restockParse.ts`,
`paymentParse.ts` (shared by server and browser). The prompts (`lib/*Prompt.ts`) only *ask*; the validators are the
*guarantee*. **If you change a prompt, change its validator and tests together.**

## Privacy

Done in the browser **before** anything is sent (`src/utils/aiPrivacy.ts`):

- Phone-like digit runs (8+ digits with optional spaces/dashes/brackets) are removed and handed back to the app for its own use.
- Names of customers the app already knows are replaced by their label (`C-4F2A`); a first name alone matches only if unique.
- The AI snapshot contains **no** customer names or phone numbers: customers are labels only. Product and material names
  travel as ids with a `names` map.
- Names of *new* customers and delivery addresses written in a message being read do reach the model, because reading
  them is the point.
- The server logs token usage and stop reason for each call, never text, names or amounts.
- Demo accounts never reach the model; the briefing shows a sample built from demo data by the same code.
- Phone voice: speech-to-text happens on the phone (Google's recogniser on Android, which may send audio to Google); the server
  only ever sees the text the owner reviewed and chose to "Read".

## Who may use AI, and the caps (`lib/aiGuard.ts`, `lib/aiConfig.ts`, `lib/aiUsage.ts`)

Every model-calling route goes through one server-side check, in this order (cheapest and most decisive first):

1. **Switched on?** `AI_FEATURES_ENABLED=true` and `ANTHROPIC_API_KEY` set. Otherwise `not_configured`; nothing else in the app changes.
2. **Not a demo account** (`demo_<n>_<n>@bettereat.com`).
3. **Allow-list**, if `AI_ALLOWED_EMAILS` or `AI_ALLOWED_UIDS` is set: only those accounts, whatever their billing. An email counts
   only when Firebase has verified it. This is how AI is tried during the trial without opening it to every signup.
4. **Billing**: active or trialing, unless the server is in trial mode (`BILLING_DISABLED=true`), where billing cannot be the gate.
5. **Daily caps**, reserved atomically **before** the model is called.

| Variable | Default | Counts |
|---|---|---|
| `AI_CHAT_DAILY_LIMIT` | 30 | Questions per user per day |
| `AI_BRIEFING_DAILY_LIMIT` | 4 | Briefing generations (the first plus refreshes) |
| `AI_PARSE_DAILY_LIMIT` | 30 | Web order/production readings |
| `AI_QUICK_DAILY_LIMIT` | 60 | Phone voice/text readings |
| `AI_GLOBAL_DAILY_LIMIT` | 1500 | Model calls across everyone per UTC day |

A limit of `0` means "none allowed"; a blank or invalid value means the default. The per-user day is the **business's own date**
(`settings.timezone`), the global day is UTC. `reserveAiUse` increments both counters in one transaction, so two simultaneous
requests cannot both slip under a limit. A failed model call still counts (it can still cost money).

`GET /api/ai/status` tells the app whether to show AI features and how much allowance is left; it counts nothing. The
briefing card and the chat button call it and render nothing if AI is unavailable.

## The briefing, step by step

1. Browser builds the snapshot (after `dataReady`, so it never uses placeholder data) and `POST`s it.
2. Server checks entitlement (counts nothing). If **today's briefing is already stored**, it returns it (counts nothing, calls nothing).
3. Otherwise it claims the day (a short generation marker so two open tabs do not both call the model), reserves one use,
   asks the model, validates, retries once on rejection, and stores the result. A second rejection stores a `fallback`
   marker so the app builds the text itself.
4. The browser renders figure tiles and the headline from its own numbers, the model's `why` and `attention` via tokens, or the
   deterministic version.

Files: `lib/briefingRoutes.ts`, `briefingModel.ts` (call + JSON schema), `briefingPrompt.ts`, `briefingStore.ts`;
`src/utils/aiBriefing.ts` (attention kinds, validation, deterministic fallback), `src/components/DailyBriefing.tsx`.
Attention kinds: `preorder, reprice, price_move, profit_driver, wastage, low_stock, expiring, reorder_customer, unpaid`.

## Ask your business, step by step

Question prepared in the browser (names replaced, phones removed, max 500 chars, up to 4 earlier turns). The server answers
with text, or with a `scenario` request ("what if I raise croissants 10%"). For a scenario the **browser runs the calculation**
(`pricingScenario`), adds the result to the snapshot as new figures, and asks again, so a what-if costs two uses. Files:
`lib/chatRoutes.ts`, `chatModel.ts`, `chatPrompt.ts`, `src/utils/aiChat.ts`, `src/components/AskBusiness.tsx`.

## Reading messages into forms (web)

`useOrderParser` and `useProductionParser` prepare the text (redact, label), call the route, and turn the checked answer
into form values (`buildOrderForm` in `orderParse.ts`, `buildProductionForm` in `productionParse.ts`). Only accounts AI is available to see
the box. Limits: order text 1,500 chars, up to 15 items, up to 300 menu items sent (ids and names only).

## Reading messages on the phone

Covered in [The phone app](08-phone-app.md). It reuses the same readers and validators, adds two (stock bought, payment received),
detects which of the four kinds the message is (`detectKind`), asks questions where something is open, and applies answers **in
code** with no new model call (the checked `reading` is sent back with the answers, so answering is free and cannot change what
was said).

## Testing AI code

Models are injected, so no test calls Anthropic. `lib/__tests__/briefingFixtures.ts` holds sample snapshots and model answers;
validators have tests for each rule above (digit outside a token, unknown id, number words, over-long text, quantity not in the
message). When you change a prompt or schema, add a test that a *bad* model answer is rejected, not only that a good one passes.
`docs/AI_CFO_DESIGN.md` mentions an evaluation set of CFO questions on the demo account for answer quality.

## Adding a new AI feature (checklist)

1. Decide Rule 1 (words and tokens) or Rule 2 (read and check). Write the schema and the validator in `src/utils/` first.
2. Add a prompt (`lib/xPrompt.ts`) and a model wrapper (`lib/xModel.ts`) that returns `{raw, usage}` and logs usage only.
3. Add a route factory that: validates the body, calls `requireAiAccess`/`reserveAiFeature` with the right `AiFeature`, calls the
   model, validates, retries once, returns the checked result. Add a new `AiFeature` and limit if it needs its own cap.
4. Strip personal data in the browser first (`aiPrivacy.ts`).
5. Make the UI work with the feature absent (it asks `/api/ai/status`).
6. Test with a fake model, including rejection paths.
